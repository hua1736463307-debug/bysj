# 1. 项目定位与预期成果

## 1.1 研究背景

医学图像智能分析通常存在数据标注、训练环境配置、模型评估、部署推理和错误反馈流程分离的问题。针对本科医学信息工程专业，拟建设一套面向**公开医学图像**的可本地部署训推一体化平台，使单个研究者可以完成从数据导入到模型迭代的端到端流程。

本项目定位为**面向医学图像研究的教学与实验系统**，不作为医疗器械或临床诊断工具，不声称检测结果可替代医生判断，也不存储真实患者的个人敏感信息。

## 1.2 课题目标

1. 设计模块化的 Web + API + GPU Worker + PostgreSQL 系统架构，消除原有大型单文件和行业业务强耦合。
2. 实现医学数据集导入、标注、数据验证、来源追踪、版本冻结及训练集划分。
3. 实现 YOLO 目标检测模型的任务化训练、模型评估、结果记录、模型注册及图像推理。
4. 完成推理结果人工复核、错误样本回流与再训练，形成**反馈闭环**。
5. 以公开血细胞显微图像作为主要医学任务，完成训练、部署、系统性能与软件功能验证。
6. 形成完整、可复现的毕业设计成果：源码、运行文档、数据库设计、测试记录、实验报告、论文与答辩演示。

## 1.3 范围与优先级

| 优先级 | 内容 | 毕设地位 | 验收要求 |
|:--|:--|:--|:--|
| P0 必须 | 数据集管理、BBox 标注、YOLO 检测训练、评估、模型中心、单张/批量图像推理、结果保存 | 核心系统 | 端到端跑通，过程可追溯 |
| P0 必须 | 医学数据来源记录、三集隔离、模型与数据版本关联、部署文档、测试 | 医学信息学特色 | 可复现实验与验收 |
| P1 建议 | Polygon 标注与实例分割、人工复核反馈、版本回流、训练实验对比页面 | 完整性与论文亮点 | 至少完成反馈闭环；分割视资源决定 |
| P2 可选 | 主动学习采样算法、多数据集、多模型适配、复杂资源调度、DICOM 处理 | 研究扩展 | P0 全部通过后再开发 |

# 2. 原仓库审查与重构决策

## 2.1 已有工程资产（以审查版本为准）

- 技术体系：Vue 3、Element Plus、Vite、FastAPI、PostgreSQL、PyTorch、Ultralytics、Docker Compose。
- 已存在：`backend/dataset_versioning.py` 数据集校验、哈希、来源组划分；`backend/annotation_export.py` 标注导出；`backend/job_store.py` 数据库任务状态机；`backend/training_worker_service.py` 独立训练服务；`backend/model_registry.py` 模型 SHA256 与来源；`backend/inference_service/app.py` 独立推理服务。
- 现有核心界面：`frontend/src/views/Annotation.vue`、`Training.vue`、`DatasetManager.vue`、`ModelHub.vue`、`Inference.vue`。
- 核心重构目标：`backend/yolo_api.py` 约 16,290 行、`Annotation.vue` 约 5,200 行，需以渐进式拆分替代一次性重写。

## 2.2 确认存在的工程问题与处理原则

| 编号 | 当前状态 | 重构措施 | 完成判据 |
|:--|:--|:--|:--|
| R01 | `requirements.txt` 与历史锁定依赖契约不一致 | 统一运行依赖与镜像，恢复锁定机制 | 洁净环境依赖安装和 CI 通过 |
| R02 | 当前 Dockerfile 与发布 CI 的固定基础镜像要求不一致 | 修正构建/发布契约，修复 `release.json` 链路 | 前后端全量构建、发布版本可追溯 |
| R03 | `yolo_api.py` 过大，API 与业务代码耦合 | 拆分 APIRouter、Service、Repository | 既有核心接口契约测试通过 |
| R04 | `Annotation.vue`、`Training.vue` 文件较大 | 组件化，拆分状态及 API 通信 | 无数据丢失、功能回归通过 |
| R05 | 图像切片代码依赖手机/工牌领域模块 | 拆分通用 tiling/geometry，删除行业命名 | 标注坐标转换正确、切片可逆 |
| R06 | 独立推理服务仅明确支持 `detect` / `pose` | 先保障 detect，P1 加入 `segment` 和 mask 输出 | 检测结果格式稳定；分割另行测试 |
| R07 | 现有反馈偏向行业行为告警 | 新建医学图像级审阅、标注复核与数据回流 | 反馈不会直接污染测试集 |
| R08 | 训练代码含 `deterministic=False`，重现性不足 | 固定 seed，记录所有环境与随机设置 | 同条件多次训练记录可检查 |
| R09 | 前端全局 axios/fetch 兼容逻辑较复杂 | 统一受控 API Client 和授权处理 | 401、超时、权限回归通过 |
| R10 | 仓库包含多个运行环境源码快照与旧文档 | 冻结来源，清理毕业版入口与文档 | 独立仓库只有一套权威可构建源 |

**重要：**上述结论来自静态代码审查，不意味着已执行本地 Docker/GPU 验收。阶段 PR-00 必须先建立能真实运行的基线。

## 2.3 重构策略

采用“**绞杀式重构（Strangler Pattern）**”：优先让原核心功能保留可用接口，再逐项迁移到独立模块。每次只拆一个功能域，利用自动化测试验证行为等价；删除旧业务模块应在不再被引用、且核心流程验收通过后进行。

禁止在重构首阶段同时：替换全部技术栈、重建数据库、更换模型训练框架、删除全部旧接口。避免发生无法定位的系统性回归。

# 3. 系统用户与功能需求

## 3.1 用户角色

| 角色 | 操作权限 | 典型场景 |
|:--|:--|:--|
| 管理员 | 账户与存储配置、系统运行监测、模型管理 | 维护系统并查看全部实验 |
| 研究用户 | 管理自己的数据、训练和推理实验 | 创建医学数据集，训练模型，评估结果 |
| 标注复核用户（P1） | 标注与反馈审核 | 修正检测框、标记漏检/误检 |

本科单机演示允许只有管理员与研究用户两个角色，但 API 不应因页面隐藏按钮而省略服务端权限校验。

## 3.2 P0 业务需求

**F01 数据集管理：** 上传 ZIP/图像目录；限制上传量；安全解压；检查图像可读性、后缀与尺寸；识别 YOLO 检测标签，统计类别与缺失标注。提供数据集名称、来源 URL、许可证说明、来源版本与 sha256。

**F02 标注管理：** 加载图片、绘制/编辑/删除 BBox，类别管理、上一张/下一张、撤销/重做、草稿自动保存、单张/批量导出。标注坐标以原始图像为基准，统一归一化；删除要有确认和可恢复途径。

**F03 数据版本与划分：** 建立不可变 `dataset_version`；支持 `train/val/test`；切片或增强图像必须随源图像分组，禁止在不同集合之间泄漏；冻结的测试集不能通过反馈功能回流到训练数据。

**F04 模型训练：** 选择支持的检测权重、数据集版本、Epoch、Batch、Imgsz、Seed 等；启动异步任务；查看进度和日志；支持取消；错误原因可定位。任务状态由数据库统一持久化。

**F05 模型评估：** 独立执行 `val/test` 评估，保存 Precision、Recall、mAP@0.5、mAP@0.5:0.95、类别指标、混淆矩阵及测试设备信息。不以单个置信度作为学术评价指标。

**F06 模型中心：** 模型注册、检测任务类型、来源数据集、训练配置、评价结果、文件 SHA256、发布时间；不允许任意用户直接上传不可信 `.pt` 权重后加载。

**F07 图像推理：** 单张图片/批量图片推理，输出 BBox、类别、置信度、模型版本、耗时和可视化图片；可导出 JSON/CSV；结果归属用户与对应实验。

**F08 系统管理：** 登录、权限控制、健康检查、GPU 占用状态、审计日志及关键操作失败提示。

## 3.3 P1 与 P2 需求

- **P1-a 医学反馈：** 对推理结果提交 `correct`、`false_positive`、`wrong_class`、`missed_object`、`unreviewable` 等反馈；支持编辑 BBox，并保存原预测与人工修正的两份记录。
- **P1-b 数据回流：** 人工审核完成后生成新的训练数据版本；保持原数据集与测试集不变；展示前后模型结果对比。
- **P1-c 分割演示：** 根据可用时间接入皮肤病变公开数据，支持 Polygon、Mask 输出和 Dice/IoU。
- **P2-a 主动学习：** 实现随机抽样、置信度/熵不确定性抽样、不确定性+多样性抽样；固定标注预算及数据来源，验证样本效率。
- **P2-b 医学影像格式：** DICOM 脱敏与解析；在没有明确数据、测试和时间条件前不列为核心验收。

# 4. 技术架构与组件边界

## 4.1 技术选型

| 层 | 选型 | 理由 |
|:--|:--|:--|
| Web | Vue 3 + Element Plus + Vite | 与现有前端一致、降低迁移成本 |
| API | FastAPI + Pydantic | API 文档、模型验证、异步任务入口 |
| 持久化 | PostgreSQL + SQLAlchemy + Alembic | 事务、版本记录与迁移一致性 |
| 模型 | PyTorch + Ultralytics YOLO | 检测优先，实例分割扩展 |
| 任务执行 | 独立 Training Worker + PostgreSQL JobStore | 避免长时间训练阻塞 API |
| 推理 | 独立 Inference Worker（或稳定的推理 Service） | 模型缓存、资源隔离 |
| 文件存储 | 本地受控数据卷 + sha256 清单 | 简化本科部署且可追踪 |
| 部署 | Docker Compose，Windows/WSL2 + NVIDIA GPU | 与实际开发条件匹配 |
| 测试 | pytest + Vitest/前端测试 + HTTP 冒烟测试 | 兼顾代码与系统验收 |

**明确不引入：** Kubernetes、微服务网格、消息队列集群、大模型 RAG、患者电子病历、医疗设备对接。除非导师另行要求，避免超出本科毕设工作量。

## 4.2 逻辑分层

```text
[Web UI: 数据集/标注/训练/模型/推理/实验]
                |
                v
[FastAPI REST API: Auth + Validation + Domain Routers]
       |                |                |
       v                v                v
[PostgreSQL]       [文件数据卷]     [任务状态/模型注册]
                                         |
                           +-------------+-------------+
                           v                           v
                    [Training Worker]          [Inference Worker]
                           |                           |
                           +------------[GPU]----------+
                                         |
                                   [模型与结果]
```

API 层不直接运行长时间训练。GPU 同时只有一张卡时，采用**训练任务串行 + 推理显存预算控制**的简化策略，不强求多用户并行训练。

**数据库约束：** UUID/稳定 ID；`(version_id,sha256)` 可配置唯一性；删除采用软删除或引用保护；所有版本变更使用事务。禁止将权重、图像原文件、长训练日志直接存入数据库 BLOB，数据库保存路径与校验哈希。

## 5.2 医学数据分组和数据泄漏防护

- 图像级 `sha256` 去重是基础，但对同一患者、同一载玻片、同一采集序列的近重复图像不足以防止泄漏。
- 公开数据若有 `patient_id / slide_id / study_id`，优先将其映射到 `source_group`，采用**组级训练/验证/测试划分**。
- 当公开数据无来源分组信息时，明确记录数据集限制，不能声称实现了患者级独立测试；至少对重复和高度相似图像进行检查。
- 切片与图像增强产生的派生资产继承来源组与原图 split；**先划分再切片**，或按来源组原子分配，不能把同一原图切片随机分到不同集合。
- 模型优化过程中测试集只用于最终评估，不参与样本筛选、阈值调参和人工反馈再训练。

# 6. API 设计与接口契约

统一前缀 `/api/v1`，统一返回结构：`{code, message, data, request_id}`；异步任务提交返回 `202 Accepted` 和任务 ID。文件资源通过鉴权或签名方式访问，不能通过绝对磁盘路径暴露。

| 方法 | 路径 | 主要作用 |
|:--|:--|:--|
| POST | `/datasets/import` | 导入 ZIP/公开图片；创建数据集 |
| GET | `/datasets/{id}/versions` | 查看版本与数据统计 |
| POST | `/datasets/{id}/versions` | 冻结新版本并校验划分 |
| GET | `/datasets/{id}/assets` | 分页获取图片及标注状态 |
| PUT | `/annotations/{image_id}` | 保存指定修订版的标注（冲突检测） |
| POST | `/training/jobs` | 异步启动训练 |
| GET | `/training/jobs/{job_id}` | 查看状态、日志与指标 |
| POST | `/training/jobs/{job_id}/cancel` | 请求取消任务 |
| POST | `/evaluations` | 提交评估任务 |
| GET | `/models` | 查询模型列表及版本信息 |
| POST | `/inference/images` | 单张/批量推理 |
| GET | `/inference/runs/{id}` | 读取检测与可视化结果 |
| POST | `/reviews` | 反馈和人工修正（P1） |
| POST | `/reviews/export-version` | 生成复核后的新训练数据版本（P1） |
| GET | `/experiments` | 实验对比与复现信息 |

**训练任务请求示例：**

```json
{
  "dataset_version_id": "version-uuid",
  "model_ref": "approved-yolo-detect-weight",
  "task": "detect",
  "epochs": 80,
  "batch": 8,
  "imgsz": 640,
  "seed": 42,
  "device": "cuda:0",
  "project_name": "blood_cells_baseline"
}
```

**推理结果规范化示例：**

```json
{
  "model_id": "model-uuid",
  "task": "detect",
  "image_id": "image-uuid",
  "latency_ms": 35.7,
  "predictions": [
    {"class_id": 0, "class_name": "RBC", "confidence": 0.93,
     "bbox_xyxy": [12.4, 21.1, 57.8, 66.0]}
  ]
}
```

返回中的数值仅展示 API 结构，**不是实际模型实验结果**。扩展分割时新增 `mask` 或 `polygon` 字段，不在检测结果中混用。

# 7. 医学数据与模型实验方案

## 7.1 核心案例：血细胞目标检测

**公开数据集：**BCCD（Blood Cell Count and Detection），源仓库 `https://github.com/Shenggan/BCCD_Dataset`。公开版本约 364 张显微图像，提供 RBC、WBC、Platelets 三类检测框，原公开仓库声明 MIT 许可。正式下载时须核对图片、标注来源和当前许可文件。

**数据处理：**VOC/XML → 标准 YOLO 检测标签；校验类别映射、框是否越界、空标签、重复图像；生成数据集 `manifest.json`、统计报告及归一化标签。标签转换必须保留精确类别 ID，不得因读取顺序造成错位。

**局限性：**数据量较小，容易产生过拟合或偶然的测试结果；建议把它作为系统主流程的验证数据，不把单次高精度解释为临床可靠性。若实验不足，可在完成来源和许可核对后补充 TXL-PBC 等公开研究数据，但不得简单合并不同标签体系且不说明数据来源。

## 7.2 扩展案例：皮肤病变分割（P1）

ISIC 2018 官方 Task 1 提供皮肤镜图像与病灶边界标注，可作为医学分割适配验证。应记录版本与使用条件。仅在检测主流程、独立推理服务和标注几何规范稳定后接入，避免同时处理两个任务导致项目失控。

**注意：**YOLO 检测数据集的 BBox 标签不能直接作为实例分割训练标签。Polygon/Mask 格式、类别数与模型 `task=segment` 必须严格对应。

## 7.3 模型实验与基线

**模型路线：**首先选一个受支持、可合法使用的轻量级 YOLO 检测权重作为统一基线，如平台锁定依赖兼容的 `yolo26n` 或 `yolo11n`。不要在实验中更换模型版本却仍称为同一基线。

**建议首轮配置：**`imgsz=640`、`batch=8`（按显存调整）、`epochs=80`、`seed=42`、早停启用；数据划分、版本、增强和预训练权重固定。记录 `Python/Torch/CUDA/Ultralytics` 版本、GPU 型号、代码 SHA、数据集版本和训练配置。后续比较训练策略时，尽量进行 3 个随机种子实验，报告均值和标准差。

**必须输出：**类别数量和分布、训练 loss 曲线、混淆矩阵、P/R、mAP50、mAP50-95、每类指标、GPU 显存与推理延迟。

## 7.4 论文的最低实验组合

| 实验 | 组别 | 必须控制的变量 | 结论依据 |
|:--|:--|:--|:--|
| E1 基线训练 | 固定版本与参数下的检测模型 | 数据与 seed | 模型是否可完整训练与推理 |
| E2 数据处理对比 | 原图训练 vs 通用切片/增强 | 模型、训练预算、划分一致 | 小目标类别的 Recall、mAP、性能代价 |
| E3 反馈闭环 | 初始模型 vs 加入复核后样本的模型 | 独立测试集不变 | 反馈是否产生可测收益 |
| E4 系统性能 | 图像上传、标注保存、训练任务、推理 | 硬件环境和输入规模记录 | 吞吐、延迟、失败率和资源消耗 |

若 P2 主动学习获导师认可，再追加 **E5：相同标注预算下，随机选样 vs 不确定性选样 vs 多样性联合选样**。不以事先假定“改进必须有效”为结果，允许如实报告无显著改善的实验。

# 8. 核心模块开发细则与验收

## 8.1 数据集与标注

- 数据上传先落临时隔离区，验证后才进入正式数据卷；解压需拦截路径穿越和异常压缩比。
- BBox 使用标准 `class cx cy w h`；Polygon 使用 `class x1 y1 ... xn yn`，标注格式依据任务验证。
- 标注草稿具备修订号，避免多窗口保存相互覆盖；每次审核留下审阅人、时间和前后内容。
- 数据版本冻结后只读，后续修改创建子版本，保持原实验引用一致。

**验收：**导入含有少量正常、空标签、越界标注的测试样本，错误可定位到图片/行号；保存与重载后标注坐标一致；切片与导出标注没有偏移；同一来源组不会跨训练/验证/测试集。

## 8.2 训练与模型注册

- 复用当前 JobStore 的合法状态流转：`pending → running → completed/failed/cancelled`，处理中断恢复必须明确。
- Worker 训练前验证 GPU、模型 task、标签 geometry、数据集版本与路径；任务启动采用 spawn 隔离，避免 CUDA fork 问题。
- 训练结束保存配置、指标、日志、权重 sha256、数据版本；模型缺失时页面显示状态，不伪装为可用。
- 外部上传权重默认禁用；仅允许受信任来源、经校验的模型进入模型中心。

**验收：**测试正常完成、非法标签拒绝、GPU 不足排队/明确失败、用户取消、服务中断后的状态恢复；模型来源追踪准确。

## 8.3 推理与评估

- 优先跑通检测 `detect`；P1 实施统一适配器 `ModelAdapter`，定义 `load / predict / validate / release`。
- 每条推理结果保留 model_id + image_sha256 + inference_params + runtime_version + timestamp。
- 图像显示可叠加预测框，支持显示类别、置信度、框数量和统计结果；模型结果与人工标注区分颜色/图层。
- 批量推理需分页/任务化，不通过单个 HTTP 请求同步处理无限数量图片。

**验收：**同一张图相同模型与设置输出结构稳定；单图、批量运行和导出通过；不可信文件、错误图片或超限上传收到明确 4xx 错误而非进程崩溃。

# 9. 安全、合规与可复现要求

## 9.1 公司项目使用授权

**G0 法律与学术前置门槛：**必须确认公司授权是否覆盖源代码复制、重构、个人开发环境部署、毕设展示、论文插图以及可能需要向学校提交源码等行为；不得因仓库位于个人 GitHub 账户就推定个人拥有著作权。若授权范围不足，则使用独立实现路线。

严格排除公司业务数据、摄像头地址及账号、密钥、私有模型权重、录像、内部文档和相关部署环境配置。对新仓库执行敏感信息扫描；仅保留示例变量和人工生成的测试样本。

## 9.2 平台安全措施

- 服务端对所有数据集、模型、训练、推理结果执行用户/角色权限验证；不依赖前端隐藏按钮。
- 文件上传进行类型、大小、解压比例、路径穿越、文件数量和图像像素上限检查。
- 非信任 `.pt` 模型反序列化风险较高，普通用户不得任意上传后立即载入。
- CORS 按毕业版源站收敛；检查 WebSocket、静态资源与模型路径访问控制。
- 数据库迁移以 Alembic 管理；禁止以生产数据直接测试破坏性迁移。

## 9.3 重现实验清单

每次训练保存：`dataset_version_id`、分组划分 seed、model_base_sha256、source_commit_sha、requirements 锁文件摘要、hyperparameters、Python/Torch/CUDA/GPU、时间戳、随机种子、指标和图表路径。测试集保持只读。`deterministic=True` 应作为研究默认候选配置，同时记录任何不得不关闭的算子或性能原因。

## 11.1 PR-00 首批工作指令（可直接交给 Codex）

1. **先审计，不修改：**确认 `main` 最新 SHA、当前 Dockerfile 与依赖文件、CI、实际服务入口；列出当前构建失败的直接原因，不凭历史 README 下结论。

4. **质量门禁：**执行 Python 编译、后端 pytest、前端构建、`docker compose config`、启动健康检查，并记录失败的测试及原因。
